### 源码核对：触发行为与自动判据

已核对上传的实际 [App/can_bringup.c](../../firmware/PICO_CAN/App/can_bringup.c)，并归档两种模式的 ELF、HEX、BIN。六个产物的字节数和 SHA-256 均与工程自带的 `preparation_checks.json` 一致，核对结果见[工程导入说明](../../firmware/PICO_CAN/IMPORT.md)。该源码中的关键逻辑为：

```c
#define FRAME_COUNT 100U
/* 第一条通过校验的接收帧启动测试。 */
if (!started) { started = 1; start_ms = now; next_tx_ms = now; }

/* 启动后按约 100 ms 间隔发送，直到 next_sequence 达到 100。 */
if (started && next_sequence < FRAME_COUNT && (int32_t)(now - next_tx_ms) >= 0) {
    /* ...提交一条 0x123 测试帧... */
    ++next_sequence;
    next_tx_ms = now + 100U;
}
```

所以“一条有效 `0x321` 触发 100 条 `0x123` 返回”正是源码中的运行行为，与本轮两端记录一致。在同一份源码的末尾，自动 PASS 判据却仍同时要求 `tx_submitted == FRAME_COUNT`、`tx_completed == FRAME_COUNT`、`rx_unique == FRAME_COUNT`，并要求各项错误为 0。[check_log.py](../../firmware/PICO_CAN/scripts/check_log.py)同样保留了三个事件各 100 条及 PASS 汇总的严格规则。

本次只接收触发序号 `0x00`，所以这一自动判据报告缺少 `0x01`—`0x63`，即 `rx_missing=99`，并打印 FAIL。这不是“没有返回 100 条”；返回 100 条已经逐帧确认。单触发功能核对与程序自动判据分别记录，原文件中的 FAIL 不修改。

在这份 USBCAN 导出范围内，电脑只记录发送了 1 帧，板端也只记录收到 1 帧，两端吻合。这里的 99 是缺少的预期输入数量，不能解释为已经发送的 99 帧在物理总线上丢失；现有记录也不能给出满载条件下的丢包率。

CSV 的 `t_ms` 是开发板启动后的毫秒数，TXT 中的时间是电脑侧显示时间，两者没有提供时钟同步信息，不直接相减计算端到端时延。
