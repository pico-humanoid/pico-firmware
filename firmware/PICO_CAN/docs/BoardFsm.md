# PICO 开发板状态机验证

硬件只需 NUCLEO-G474RE 和一根能传数据的 ST-LINK USB 线。固件应用名为 `BoardFsm`，用板载 LED 和 ST-LINK 虚拟串口观察状态。电机 1、2 的确认均由测试固件模拟，FDCAN 不初始化，不发送电机报文。

## 烧录和验收

### 从 PICO 开发控制台验证

打开 **实验中心 → 保护验证 → 状态机单板验证**。接入开发板，依次点击 **编译固件 → 烧录固件**，选择 ST-LINK 虚拟串口，再点击 **连接 → 一键验证**。如果已经烧录相同固件，可以直接连接。

已烧录旧版时，先编译并烧录新版。新版启动报文及状态报文带有 `led_scheme=COUNTED`。第 5 项验收等到 `state=DEBUG_RESERVED,pending=0,ack1=1,ack2=1` 才通过；第 8 项仍会检查 `RESET → ACCEPTED`、自检开始及回到零力矩。

界面显示当前状态、两台电机的模拟确认和故障原因，并列出八项验收的预期现象与结果。一键验证依次检查自检、内置逻辑、零力矩与阻尼切换、调试预留、丢失确认后的故障锁定、锁定时拒绝切换，以及重新自检后的恢复。成功时窗口显示 **一键验证：通过 · 已通过 8/8 项**。也可用 **请求零力矩、请求阻尼、进入调试预留、重新自检** 分别操作。

下方分为 **中文运行日志、原始报文、标志说明** 三个页签。中文运行日志解释每条消息；标志说明可随时查看代码和字段的含义。`logs` 目录同时保存原始 `.log` 和带中文解释的 `_readable.log`，后者开头也附有完整说明。

点 **状态图与灯光** 查看模式切换。零力矩每组闪 1 下，阻尼 2 下，调试预留 3 下。每下亮 0.2 秒，组内间隔 0.2 秒；每组结束后熄灭 1 秒，再重复。自检、等待确认和故障锁定期间熄灭。一键验证在第 2、3、5、7 项各停留约 3 秒供观察。

### 使用独立工具

1. 通过 ST-LINK 的 USB 口接板。打开 STM32CubeProgrammer，选择 **ST-LINK**，点击 **Connect**。
2. 在 **Erasing & Programming** 中选择交付目录中的 `PICO_BoardFsm.hex`，勾选 **Verify programming**，点击 **Start Programming**。完成后按开发板 RESET。
3. 关闭占用同一串口的窗口。在交付目录打开终端，用 `python verify_board_fsm.py --list` 查看 ST-LINK 虚拟串口，再运行 `python verify_board_fsm.py COM5`。把 COM5 换成实际端口。Ubuntu 可传入实际的 `/dev/ttyACM0` 等设备路径。
4. 成功标志是 `[整体验证通过] 8/8项通过` 和 `BOARD_FSM_SERIAL_RESULT=PASS (simulated motors)`。脚本会在当前目录保存原始日志及带解释的 `_readable.log`。脚本只打开串口，烧录由操作者执行。

也可用任意串口终端，设置 **115200、8N1、无流控**，每条指令发送换行。先打开串口再按 RESET 查看启动输出。如果错过启动日志，可以发 `TEST` 重跑内置逻辑用例，或等周期状态输出。

| 操作 | 预期结果 |
| --- | --- |
| 上电、按 RESET 或发送 `RESET` | `SELF_CHECK`。先看到一台确认，等两台都确认后进入 `ZERO_TORQUE`，板载灯每组闪 1 下。串口 `RESET` 只重跑逻辑自检。 |
| 发送 `DAMP` | 等待两台模拟确认后进入 `DAMPING`，板载灯每组闪 2 下。 |
| 发送 `ZERO` | 等两台模拟确认后回到 `ZERO_TORQUE`，LD2 每组闪 1 下。 |
| 发送 `DEBUG` | 受理后等待两台模拟确认，进入 `DEBUG_RESERVED`，LD2 每组闪 3 下。本版只验证状态切换；可以发送 `ZERO` 或 `DAMP` 离开该状态。 |
| 在零力矩状态依次发送 `MISS2`、`DAMP` | 只收到 `ack1=1`，900 ms 后 `FAULT_LOCKED`，原因为 `MODE_TIMEOUT`，板载灯熄灭。此时 `ZERO`、`DAMP` 和 `DEBUG` 均被拒绝。 |
| 在故障锁定时发送 `RESET` | 模拟故障为一次性，重跑自检并恢复到零力矩。也可在正常状态依次发送 `MISS1`、`RESET` 模拟开机自检超时。 |

`FSM_STATE` 的 `source=SIMULATED` 标识反馈来源。`state` 表示当前状态，`target` 是本次请求目标，`pending=1` 表示正在等待确认。即使其中一台已经回复，两台都确认之前也不提交新模式。超时后需要手动复位，迟到确认不会解除锁定。

板端自检检查串口配置，运行状态转换用例，并等待测试固件生成两台模拟确认。它验证状态机与界面可观察行为。实际电机的零力矩、阻尼、驱动反馈和 CAN 另行上台架验证。

## 日志怎样读

| 标记 | 含义与判定 |
| --- | --- |
| `[电脑发送]` | 已向开发板的USB串口发出请求。 |
| `[板端答复]` | 开发板的受理结果。`ACCEPTED`只是受理，还要等两路确认。 |
| `[等待确认]` | `pending=1`，目标模式尚未完成切换。 |
| `[状态到达]` | 板端报告当前状态；这条消息本身不代表全部实验通过。 |
| `[状态心跳]` | 状态未变的周期报告，中文日志约10秒记一次，原始日志保存全部。 |
| `[逻辑用例]` / `[内置检查]` | 单项用例或板端内置检查通过，不等于整套串口验收通过。 |
| `[故障注入]` | 一键验证故意让第2路漏回确认。 |
| `[观察灯光]` | 当前状态停留约 3 秒，方便观察 LD2。 |
| `[预期保护]` | 本次故障测试中出现的超时锁定或锁定拒绝；还要检查随后恢复。 |
| `[异常报警]` | 非预期故障、报文异常或拒绝请求，需要检查。 |
| `[步骤通过]` / `[步骤失败]` | 八项验收中的某一项结果，失败后后续步骤不执行。 |
| `[整体验证通过]` | 八项全部完成，最终恢复零力矩，两路模拟确认都收到。 |

`#` 只是开发板日志的行首标记，不代表错误；`>` 标记电脑发送的指令。`FSM_STATE` 是状态记录，`FSM_REPLY` 是指令答复，`FSM_CASE` 是单项内置检查，`FSM_TEST_RESULT` 是板端内置检查汇总，`BOARD_FSM_SERIAL_RESULT` 才是整套电脑串口验收结果。

例如原始记录（原本为一行，这里分行排版）：

```text
# FSM_STATE,t_ms=1300,source=SIMULATED,state=ZERO_TORQUE,
target=DAMPING,pending=1,ack1=1,ack2=0,fault=NONE,drop_next=0
```

这表示开发板已运行1.300秒，当前仍是零力矩，正在请求阻尼；只收到模拟电机1的确认，还没收到模拟电机2的确认，所以没有切换成功。`fault=NONE` 表示此时没有故障。`drop_next=0` 只表示没有为下一次切换安排漏回确认，不说明本次是否正在进行故障注入。中文日志会将这条记录标为 **等待确认**。

当后续出现 `state=DAMPING,pending=0,ack1=1,ack2=1,fault=NONE`，才能确认阻尼状态已到达，用户灯每组闪 2 下。进入调试预留同样以 `state=DEBUG_RESERVED,pending=0,ack1=1,ack2=1` 为准。自检、等待确认和故障锁定期间 LD2 熄灭。

一键验证第6项会发送 `MISS2` 再发送 `DAMP`，主动让第2路漏回确认；900毫秒后故障锁定属于本项的预期保护。第7项检查锁定时拒绝 `ZERO` 和 `DEBUG`，第8项发送 `RESET` 重跑自检恢复。只看到故障锁定不能判定整个实验成功，必须等 **8/8项通过**。

## 从源码重建

在固件工程根目录执行以下命令，使用工程已有的 Arm GNU、CMake 与 Ninja。

```powershell
cmake -S . -B build/BoardFsm -G Ninja '-DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake' '-DCMAKE_BUILD_TYPE=Debug' '-DPICO_APP=BoardFsm'
cmake --build build/BoardFsm
```

产物为 `build/BoardFsm/PICO_CAN.hex`、`.elf` 和 `.bin`。状态转换实现在 `App/board_fsm.c`，板端 UART 和 LED 在 `App/board_fsm_app.c`。共享用例既可随固件执行，也可用现有的主机 CMake 测试工程运行 `test_board_fsm`。
